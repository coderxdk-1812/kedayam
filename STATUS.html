How useful is this really? (honest assessment)

⚖️ The one-line truth

Every Chrome user already has Google Safe Browsing — a huge, always-updated cloud backend. So Kedayam's real worth is what it adds on top of that, as a defense-in-depth second layer — not as a replacement. Judged that way it is genuinely valuable in a few specific gaps, and redundant for plain known-phishing URL blocking.

Where it adds real, differentiated security (uplift over a stock Chrome + Safe Browsing setup):

  • ClickFix / fake-CAPTCHA clipboard malware HIGH uplift — the dominant 2024–25 delivery trick. AV and Safe Browsing largely miss it because the user runs the payload. Kedayam intercepting the copied command is rare and genuinely protective.
  • Accidental sensitive-data leaks (paste/file/form guard) HIGH uplift — stops pasting a password / API key / card / PII into a phishing form or the wrong site. Nothing in the baseline does this.
  • Homoglyph / IDN visual spoofs (аpple.com) MED uplift — catches zero-day Unicode look-alikes the human eye can't distinguish.
  • Privacy & transparency MED uplift — 100% on-device, zero telemetry, on-page explainable warnings (says why). A real differentiator vs. cloud tools that upload your browsing.
  • Brand-in-subdomain / abused-TLD / open-redirect MED uplift — solid supplementary URL-shape signals.

Where it is weaker than incumbents / honest limits:

  • Blocklist scale — ~20k baked hosts vs. millions in commercial cloud feeds. Without the opt-in refresh, pure URL-reputation coverage is thin and goes stale.
  • No cloud intelligence by default — can't see brand-new global campaigns the way a cloud backend (Safe Browsing) can within minutes.
  • The classifier is now trained & MEASURED on a 12k labeled corpus (Phishing Army/OpenPhish vs. top-sites): precision 0.98, recall 0.62, FP 1.4% at the warn threshold (host-URL shape, no live DOM). It catches structural phishing but misses ~40% of kits that look benign by hostname — hence a corroborating layer, not a standalone blocker. The cert's recall is now this measured figure, not a placeholder.
  • Overlap — for blocking already-known phishing URLs it is largely redundant with Safe Browsing.

👤 Who benefits most, and rough uplift

Big benefit: users targeted by ClickFix / fake-captcha lures; anyone who handles secrets or PII (developers, finance, support staff); privacy-conscious users who won't run cloud AV extensions.

Modest benefit: a careful user already on Safe Browsing “Enhanced” + a password manager — the marginal gain is small for plain phishing, but the ClickFix and data-leak guards still cover gaps nothing else does.

Rough, unvalidated estimate: near-zero → strong coverage on ClickFix & accidental data-leaks (little/no baseline), +a modest slice of the long-tail phishing Safe Browsing misses. These are engineering estimates, not a measured benchmark — see “What next”.

What next — to make it better & best

Tier 1 — biggest security ROI (do first)
  • ✅ Measure & train the classifier — DONE. Fitted on a 12k labeled corpus (bun run train:classifier), monotonic non-negative model; measured P 0.98 / R 0.62 / FP 1.4% @warn, published to the cert. DOM-corpus recall lift attempted (bun run train:classifier:dom): infra built with a login-page guard, but the live crawl was too thin (72 phishing + 3 login pages) so the expert priors were kept — no regression. Next: a curated saved-HTML corpus.
  • ✅ ClickFix hardening — DONE. Hooks the deferred/on-click write paths (clipboard.write / DataTransfer.setData), adds a one-click "Clear my clipboard", and broadens command/lure signatures.
  • Bigger, signed, delta-updated blocklist baked per release + auto-refresh default-on using privacy-preserving hash-prefix (k-anonymity) lookups — cloud-grade coverage without sending full URLs.
  • Redirect-chain resolution for shorteners — score the true landing before render.

Known gaps & caveats

  • Broad host_permissions + webRequest + tabs → Web Store extended review; needs a tight single-purpose justification.
  • Classifier recall is measured but host-URL-shape only (no live DOM in the corpus): ~62% @warn. Real-page recall is likely higher (DOM signals help) but is not yet benchmarked; the corpus is also a point-in-time feed snapshot.
  • The committed zip is a checked-in binary built on macOS; the zip CLI is not byte-identical across OSes, so CI verifies the zip's contents match source (scripts/verify-artifact.mjs) rather than a byte-for-byte rebuild. The cert stays byte-reproducible.
